# Design notes: macros, packed hitlists, sweep layout

Design decisions and the measurements behind them. The earlier planning documents for macros and packed hitlists were merged into this file on 2026-10-24 (full text in git history). Numbers are in `Claims.md` and `Benchmark/`. State as of 2026-10-25.

## 1. Macros (implemented, not committed)

A macro is a native block that stands in for a gate-level subcircuit (kinds so far: `dff`, `dffsr`). It reduces size (a gate-level DFF is 10 gates), gives glitch-free evaluation, and keeps every state readable through the API. Measured: macro flops against gate-level flops make rx-prop about 1.5 to 1.7x faster per suite (ISCAS89 1.58 to 1.82x), with 0 mismatches against Icarus on all suites.

**Pieces**

| Piece | What it is |
|---|---|
| macro gate | `MacroGate(Gate)`, type `MACRO_GATE_ID = 12`, `TOTAL = 13`. Holds `kind`, `outs`, and the core pointer in `hitlist.data` (`size = 0`, `capacity = 0`, so the loops never walk it). |
| inputs | Ordinary edges from the sources into the macro gate, in pin order. |
| output pins | The IC's own `IC_OUTPUT_PIN` gates with no source, written directly by the core. `connect` refuses a macro gate as a source and the pins as targets. |
| `MacroCore` (`reactor/Macro.h`) | C++ base class: `n_in`, `n_out`, input and output locations, `memory[]` (each input's value at the previous evaluation), `changed[]`, `init`, virtual `eval(G, self)`, `reset()`. Adding a kind is one subclass and one table entry (`MACRO_KINDS`, `make_core`). |
| packaging | `make_macro(kind) = load_ic(macro_map(kind, init))`: an ordinary IC (input pins, macro gate, output pins) that the UI draws as a block. `DFF.json` (init 0) and `DFFSR.json` (init X) are macros; `*_gate.json` keep the gate-level flops for tests. |

**Behaviour**
* **Dispatch.** One type test per pop (not per edge) in `propagate`, both phases of `sweep` and `complete_task`. The engine sets the macro gate's output to `MACRO`, calls `m.eval(...)`, counts the changed output pins in the evaluation count, and queues them. Cost for circuits without macros: one never-taken branch per popped gate (measured within 0.3% of the previous build).
* **Queueing on every input change.** The engine queues a gate when `evaluate()` returns a different output from the stored one, and for a macro gate `evaluate()` only reflects the parity of the inputs equal to 1, so a change such as unknown to 0 does not alter it. Before each core call the engine therefore stores `MACRO` (= 3, defined next to `UNKNOWN = 2` in `Const.pxd`) in the macro gate's output. `evaluate()` produces only 0, 1 or 2, so the next input change differs from the stored value and the macro is queued again; the core compares its inputs with `memory`. The value has to differ from 2 as well, because the engine writes 2 into a target whose source went unknown: with `MACRO = 2` an input going unknown no longer queues the macro (tested). Storing before the call matters for speed: the same store after the call cost 1 to 3.5% on circuits without macros through code generation, before the call 0.
* **Alternative measured and not adopted.** A per-edge `force` byte (in the unused bytes of `Profile`) that ORs into the queue test works equally well but costs 6 to 10% on every circuit, including those without macros. The flags-bit variant tested on the target cost 4 to 8%.
* **Edge detection and the shift-register race.** Outputs are visible as soon as the macro gate pops. A core detects the clock edge from the current clock value (`memory[CK] == 0 && ck != 0`) and samples D from `memory`, the value at its previous evaluation, so flops clocked by the same edge all sample before any of them changes. With the current D instead, a shift chain matched the gate-level flop in 8 of 16 runs (sweep). Limit: a data change in one wave and the clock edge two or more waves later samples the new data, as in a zero-delay gate-level netlist.
* **Unknown values and power-up (decided 2026-10-26).** A DFF (no reset pins) starts at 0 on its first evaluation (`q.output == 1`); a DFFSR keeps an unknown Q unknown until a clock edge or an asynchronous input loads it. There is no separate start-up step and the `init` value stored in the circuit files is no longer used by the cores. At the clock edge the DFF core samples D as it is (an unknown D gives an unknown Q); the DFFSR core samples an unknown D as 0 (`memory[D] == 1`). Reasoning: a flop that can be reset is expected to be, while a flop with no reset pins has no other way to get a defined start and so behaves like an FPGA register with a defined initial value. Verified against Icarus on the tv80 Z80 workload (0 of 1,278,872 compared bus bits differ) and on b07, b14, b15, b17, b20, usb_phy, aes_core, wb_dma, mem_ctrl, pci_spoci_ctrl, sasc, spi and i2c. Variants measured and not adopted: starting every unknown Q at 0 (the gate-level flop resolves to 0, as does Verilator by default) leaves the tv80 program correct but 223,618 of 1,278,872 bus bits differ from Icarus from half-cycle 25, because Icarus keeps non-reset flops at `x` until they are clocked; and sampling an unknown D as unknown in DFFSR leaves mem_ctrl with 181 (propagate) and 124 (sweep) mismatches against Icarus, which the `== 1` line avoids (investigated 2026-10-25, cause still open: all mismatches fall on the first vector after the reset phase, on control flops Icarus holds at 1 and Darion at unknown or 0; during the reset phase no gate is unknown although the standard rule gives a known value from its current inputs, and propagate and sweep agree on every named net under the benchmark runner's stimulus). Real hardware powers unreset flops up to arbitrary values, 4-state simulators start them at `x` and Verilator at 0 or random (measured 2026-10-25), so no single start value is the real-world answer and an unknown/zero/random setting remains an option (`TODO.md`). Against Verilator (2-state, every flop starts at 0; state compared from vector 50, `verify_state.py`, propagate and sweep identical, 2026-10-26) the plain-DFF-at-0 rule gives 0 mismatching bits on b07, b14, b15, b17, b20, usb_phy, pci_spoci_ctrl and spi, and 242,517 (sasc), 319 (i2c), 4,968 (aes_core), 1,347,708 (wb_dma), 5,662,016 (mem_ctrl); starting every unknown Q at 0 gives 0 on sasc and i2c and 2,825, 174,524 and 180,000 on aes_core, wb_dma and mem_ctrl. None is exact on those three designs (not investigated; wb_dma has a known uninitialized register).
* **DFFSR.** RN = 0 resets and wins over SN = 0; otherwise SN = 0 sets; otherwise an unknown RN or SN gives an unknown Q; otherwise a rising clock edge loads D (an unknown D loads 0). Compared with the library cell `DFFSRX1` in Icarus over all 81 combinations of previous Q, RN, SN and D in {0, 1, unknown} (measured 2026-10-25), the macro differs in 18: the cell uses a "possible outcomes" rule for an unknown RN or SN (the result is known if every outcome agrees, for example D = 1 with RN = 1 and an unknown SN gives 1), and gives unknown for an unknown D; the macro gives unknown or 0 there. A version that implemented the cell's rule (75 of 81 equal) was written and removed because no design check depends on it: tv80 and the 13 IWLS designs give identical results with and without it, and the cases only occur briefly at power-up.
* **Sort and optimize.** Macro gates are collected during `_topological_sort`; `sync_core` refills the core's locations afterwards. `build_ic` keeps a macro's output pins (retyped to `BUFFER`).
* **Locations, not pointers, inside the core,** so the gate-vector growth in `Store.get` needs no fix-up.
* **Timed mode.** The macro gate's delay is 0 (`Global_delay[MACRO]`, arrays sized 13); the dispatch exists in `complete_task`.
* **Sweep and macro flops.** A macro's Q writes are back edges (the Q pins are roots placed before the macro gate), so 28 to 38% of sweep's evaluations on b15, b17 and s38584 run through the propagate fallback.
* **Evaluation counts.** `eval_count` includes the output pins a macro changed (two per flop change), in all three modes, so macro designs report 0.4 to 4.4% more evaluations than before in propagate.

**Verification (2026-10-25):** integrity 28,265 passed; timing suites unchanged; state against Icarus 0 mismatches in propagate and sweep on b07, b14, b15, b17, b20, usb_phy, aes_core, wb_dma, mem_ctrl, pci_spoci_ctrl, sasc, spi and i2c; macro flops against the gate-level `DFF_gate.json` and `DFFSR_gate.json` from power-up in toggle, ring, Johnson, swap and counter circuits (10 of 10 identical), plus DFFSR single flop, shift chain, ring and counter scenarios (16 of 16 identical each); unknown-clock cases; 0 wave-limit hits on 12 macro designs from power-up; an oscillating ring clocking macro flops behaves the same as before.

**Known differences from the gate-level flop (not resolved).** After an input pin is disconnected or a neighbouring flop is hidden, the gate-level flop turns unknown (its gates propagate X through held state) while the macro keeps its state. Cutting RN or SN makes the macro Q unknown until the pin is reconnected and then resolves to 0, whereas the gate-level flop keeps clocking. An unknown clock currently counts as a rising edge (`ck != 0`). A read of the macro gate's own output returns `MACRO` (3).

**Decisions and rationale:** C++ virtual `eval`, not Python (no GIL in the loop); not inherited from IC (a macro is a gate, the IC only packages it); no separate output type (IC output pins); no library UDP emulation (a plain DFF kind, verified against Icarus instead); no seeding at start.

**Not built:** combinational macros, RAM/ROM, bus multiplexer, high-impedance values, UI drawing of macros, macros inside user-created ICs (`build_ic` keeps the macro in simple cases; nested save and load is untested).

## 2. Packed hitlists (implemented, not committed)

After `optimize()` reorders the gates, every gate's fan-out list is copied into one block in gate order, so a wave walks the edges in memory order.

* **Ownership is carried by the sign of `capacity`** (`int32_t`): positive means the list's own malloc'd array with that many slots (freed with the list, grown by realloc); negative means a slice of the packed block with `-capacity` slots (never freed; appends after removals stay inside the slice, and when it needs more it mallocs a new array, copies and turns positive); zero means no storage (empty, or a macro gate's core pointer with `size = 0`). `slots()` returns the slot count for either sign. Removing an edge only lowers `size`; repacking in the next `optimize()` returns the memory. `uint32_t` sizes stay (vga_lcd's clock fan-out is 33,833).
* **Earlier encoding and the bug it hid.** The first version marked a slice with `capacity == 0` and `size > 0`. `grow()` then sized the new array at 2 entries regardless of the slice length, so any edit after `optimize()` that added an edge to a gate with two or more fan-outs overflowed the heap (found with AddressSanitizer in the edit fuzz, 2026-10-25). The signed capacity removes the ambiguity.
* **Mechanism.** `pack_gate` in `reactor/Profile.h`; the block is `Circuit.edge_block`, created only in `optimize()`, freed after the old gate vector is cleared, and by `clearcircuit` and `__dealloc__`. The gate struct (24 B), `Profile` (16 B) and the hot loops are unchanged.
* **Result.** The packed edge store is 1.5 to 1.75x smaller (no malloc headers or rounding). On a clean heap the old `optimize()` already placed lists almost in order by accident (97 to 100% adjacent), so the speed gain is 1.03 to 1.09x there; on a fragmented heap 1.27x (vga_lcd up to 1.61x). On real netlists scaled past the L3 size the gain peaks near the cache size (1.1 to 1.3x, DRAM fills down 1.3 to 2.4x at identical instructions and branch behaviour). Details in `Benchmark/9700X.md`.
* **Tests (2026-10-25).** Random acyclic circuits optimized and then edited (edges added until lists outgrow their slices, a second `optimize()`) match an unoptimized twin in 240 of 240 comparisons, with no AddressSanitizer errors. With disconnects added, 26 of 240 runs differ on this build and on the build before the capacity change; the cause (partially unknown inputs) is not investigated.
* **Also found and fixed:** `Circuit.generate()` kept a pointer into the gate vector across `getcomponent()` calls; loading a second large netlist into one circuit crashed. It now indexes the vector each time.

## 2b. Connect and unknown sources (fixed 2026-10-25)

`Gate.connect` calls `process()` on a source whose output is unknown, which recomputes it (for example a NOR of an unknown and a 1 becomes 0) and wrote the new value without notifying the source's other targets. Those targets kept their old unknown output although all their inputs were known. `Circuit.connect` now propagates from the source as well when its output changed. Found with an invariant check on random circuits (a fully connected gate with known inputs must hold its function's value): 57 to 58 of 60 circuits violated it before the fix, in propagate and sweep, optimized or not; 0 of 200 after. The fix is independent of layout, so it also explains the earlier difference between optimized circuits and their unoptimized twins after edits.

Remaining differences between an optimized circuit and its unoptimized twin after disconnects (about 7% of runs): every one starts at a gate with an unknown or disconnected input. A gate whose source goes unknown is set to unknown without evaluation, while a later evaluation triggered by another input counts an unknown input as not equal to the seed (optimistic), so the output of a partially unknown gate depends on which input changed last, and that order differs between layouts. Gates whose inputs are all known always agree. Measured over all 54 combinations of six two-input gate types and inputs in {0, 1, unknown}, each reached from every start state in both orders (propagate and sweep identical; the reference table matches Icarus in all 54 entries): the 30 combinations with both inputs known or both unknown are correct and path-independent; the 24 combinations with exactly one unknown input depend on the path. In 16 of them Darion can give a definite value where the standard 4-state result is unknown (AND(1,X), OR(0,X), NAND(1,X), NOR(0,X), every XOR and XNOR); in 8 it can give unknown where the standard result is definite (AND(0,X), OR(1,X), NAND(0,X), NOR(1,X)). The standard result is among the possible outputs in every case. The optimistic evaluation is deliberate (author, 2026-10-25). Unknown is a debugging marker, not a hardware value, and a gate with some known inputs evaluates from the known ones so that cross-coupled latches, and therefore gate-level flops, start from design mode. Measured against Icarus (4-state, standard rules): a NAND SR latch with S = R = 1 from power-up stays Q = x, QN = x, and a toggle flop built from two NAND D latches stays x through four clocks; in Darion the same latch resolves to Q = 0, QN = 1 (propagate and sweep) and the gate-level flops run. Any rule that makes a gate with one unknown input unknown (the standard controlling-value rule for the cases without a controlling value, or "any unknown input gives unknown") would leave these loops unknown, as Icarus does. The path dependence is the part to resolve: a source going unknown forces the target to unknown without evaluation, while a later evaluation triggered by another input resolves it. Wrong paths in the 24 one-unknown combinations, 204 of 972 against "any unknown gives unknown" and 212 of 972 against the standard rule; neither is the intended rule, so these numbers only size the order dependence. Options and constraints are in `TODO.md`.

## 2c. IC file loading (fixed 2026-10-25)

`Circuit.get_ic` indexed `crct[LOCATION]` on any JSON file without checking its length, and `reactor/` is compiled without bounds checks. Loading a plain circuit file with fewer than three gates as an IC (the IO test `test_load_circuit_as_ic`, one NOT gate) therefore read past the end of the list, and the garbage it found sometimes looked like a list, after which `IC.configure` reserved a map of that garbage size (`std::bad_alloc`, 140737488355213 buckets, or a segmentation fault). The outcome depended on the heap layout: the committed code passed this test every time until additional tests changed the layout, and then 18 of 30 integrity runs aborted (found with `gdb` catching the throw and dumping the Python stack). `get_ic` now returns `None` unless the file is a list with at least `MAP + 1` entries, `crct[ID]` is the IC id and `crct[LOCATION]` and `crct[MAP]` are lists. Integrity runs afterwards: 40 of 40 plain and 10 of 10 under `MALLOC_PERTURB_` pass. The IO test now asserts that the result is `None` and that nothing was raised.

## 3. Sweep layout study (2026-10-23 to 2026-10-25; measured in scratch builds)

Question: which gate order should `optimize()` give sweep. The engine currently keeps the original Kahn sort; the results below were measured on scratch builds and are not in `reactor/`.

* **What sweep's cost follows.** The span of changed gates, because it scans every address between the first and last marked gate. Edge length and cache-line locality did not differ between layouts. The original Kahn sort is roughly level ordered, so one input's cone spreads across the whole array; a DFS reverse postorder is cone ordered.
* **Flop-cut designs.** DFS reverse-postorder rank as the order (or as the key of a priority Kahn) is 1.1 to 1.8x faster in sweep on designs with a flop cut (macro flops geomean about 1.19x; gate-level flop ICs about 1.2x), with identical evaluation counts and 17 to 40% fewer instructions per evaluation. `optimize()` takes about 22% longer. Prop is unaffected.
* **Structural cut and Tarjan order (2026-10-24, scratch build, 58 raw-gate designs).** A gate is a latch node if it is in a mutual 2-cycle; gates that feed a latch node are input stage; edges from a latch node to anything else are cut. This reproduces the flop-IC cut without ICs, names or flags and without running any simulation. Tarjan's component emission order, reversed, is the layout. The original Kahn sort is kept when there are no latch cores and no macros, or when more than a tenth of the gates are in components larger than 64. Sweep, original against this layout: geomean 1.277x over 58 designs (1.319x on the 34 runs of 5 ms or more), 57 faster by more than 3%, none slower, best b19 1.60x; `optimize()` total 486 to 532 ms. Combinational circuits take the original path (0.97 to 1.04x, same order, noise); the same Tarjan order without the guard measured 0.85 to 0.95x on arbiter, bar, adder, priority and router.
* **Cases not covered.** Latches whose state is held in loops without a mutual 2-cycle are not detected (the original sort runs, with no gain). Dense, uniformly clocked arrays built by hand (LFSR, Johnson counter, latch counters) were 3 to 26% slower, and no static rule separated them from realistic designs. Raw-gate flops under the earlier hybrid order lost up to 23% (b14 0.77x).
* **Verification of the Tarjan layout (scratch build).** 42 of 43 IWLS raw designs 0 mismatches against Icarus (mem_ctrl has 11,511 mismatches with both the old and the new order); 1,312 random circuits with edits after `optimize()` 0 differences; integrity 28,132 passed (the suite before the macro and edit tests were added); timing suites unchanged.
* **Measured and not pursued.** Level or index keys (worse), GSIM-style grouping rules (chain rules lowered speed, sibling rule neutral), a profile-guided co-activation order (never better than DFS rank), bitmap or window skip structures (6 to 13% on sparse designs, a loss on dense ones), islands (no effect on real netlists).
* **Constraints on any future layout.** `optimize()` runs no simulation, so cuts and costs are structural; the layout must not depend on IC names or on ICs and has to work for flip-flops built from raw gates. Prior art: LECSIM, EPICS, ESSENT, partial-scan feedback vertex sets (`Related_Works.md`).
