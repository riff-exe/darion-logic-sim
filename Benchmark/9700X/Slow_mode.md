# Zen 5 (Ryzen 7 9700X): struct-size repeat and the slow-mode investigation (2026-10-21/22)

**Update 2026-10-22, idle machine:** the same configuration in one process with 9 repeats (`Ablation_synth.md`) gave d 12.85, e 26.81, g 43.44 and a 84.9 ns, the original single-call values; the higher numbers below were taken with desktop activity running and are the subject of this investigation.

Moved here from Claims.md (Claim 13, item 4) on 2026-10-22 to keep the claim readable; the claim keeps a short summary. Harness: `tests/ablation_layout.cpp` built with `g++ -O3 -march=native -std=c++20`, chain topology, 1M gates, shuffled placement with `--frag 192`, 8 iterations, 5 reps, pinned to core 2, unless stated otherwise. Scratch scripts (`slowmode_root.py`, the THP wrapper, the co-runner) lived in the session scratchpad and are not in the repo.

*Repeated across processes (2026-10-21, Zen 5, 7 separate processes pinned to core 2, chain, 1M gates, shuffled, `--frag 192`, 8 iterations, 5 reps; SMT sibling online, IDE open, so not a quiet run; fingerprints identical in all 7):* median [min, max] of the per-process median ns per evaluation: a heap+virtual 85.6 [85.0, 86.0], d flat24+SIMA 19.7 [18.5, 24.4], e flat32 40.2 [38.7, 44.0], g flat40 53.6 [52.8, 58.0], so e/d 2.04, g/d 2.72, a/d 4.3. The ordering d < e < g < a and the size gap hold in every process, so the cliff is confirmed; the earlier single calls (12.6-13.0, 27-29, 44 ns) were 25-35% lower in absolute terms, which is consistent with machine state (quiet versus not) and was not separated. Within a process d varied more (spread up to 83% across its 5 reps, per-process medians 18.5-24.4 ns) than a (under 2%), so a per-process mode effect is visible here too, for the 24-byte variant only. Not done: a quiet repeat with the sibling offline (needs root).

*Slow-mode investigation, Zen 5, variant d alone, same chain, 2026-10-22, desktop session and browser running (about 2% CPU):* (1) 10 interleaved process pairs, default versus transparent huge pages disabled with `prctl(PR_SET_THP_DISABLE)`: default 14.2-34.0 ns (median about 22.5), THP off 30.2-36.9 ns (median about 33), so huge pages are worth about 1.5x at this size, but the spread does not go away without them (and the default's fast end, 14-20 ns, is never reached). (2) THP is `always` with defrag `madvise`; sampling `smaps_rollup` showed the default run holds a near-constant 61-63 MB in huge pages (of 160 MB RSS) in all 10 processes, uncorrelated with its ns (19.4-29.1). (3) Forcing madvise on all malloc memory (`GLIBC_TUNABLES=glibc.malloc.hugetlb=1`, 141-143 MB in huge pages, 10 interleaved pairs) gave 21.1-27.6 ns against 18.4-26.1 default: neither faster nor steadier. (4) One process with 15 reps spans 18.1-24.7 ns, so much of the spread is between reps inside a process, not only between processes. Conclusion: huge-page coverage explains the level (THP on versus off), not the per-process or per-rep variation, so the page-placement hypothesis is not supported in the huge-page form.

*Follow-up the same day:* (5) frequency is not the cause: 16 processes ran at 5.46-5.50 GHz effective (cycles per evaluation divided by ns) while ns ranged 11.6-43.6; L1 misses per evaluation were constant at 2.00. (6) The variation is below L1: over 24 processes under `perf stat` (user-mode `l2_fill_rsp_src` events), ns per evaluation (13.6-20.3) correlates with L2 fills from DRAM at r = 0.93 (46.2M to 51.4M fills, +11%, for +49% time) and with cycles at r = 0.93; the DRAM share of fills was 0.363-0.389, so slow processes get more of their lines from DRAM and fewer from L3. Correlation, not a controlled test. (7) It only appears once the working set exceeds L3: 8 processes each, per-process medians 9.48-9.59 ns at 200k gates, 9.92-10.23 at 500k, 15.3-18.4 at 1M and 52.2-57.9 at 2M. Reading: the mode is a per-process difference in how well the working set stays in L3 (physical page placement and set conflicts are the likely cause, since the process cannot choose its physical pages), but the placement itself was not observed or controlled; run-to-run spread also differs with machine state (11.6-43.6 ns in one batch, 13.6-20.3 under `perf stat` an hour later).

*Root run (SMT sibling cpu 10 offline, browser and IDE closed, 24 processes, variant d, THP default):* a first batch gave 12.6-32.5 ns per evaluation, so the spread survives a quiet machine (its colour snapshot was missed in 14 of 24 runs by a script timing flaw, so it is not used). Repeat with the sampling fixed, all 24 processes sampled: ns 11.8-42.2 (median 14.9). The physical-page colour map (L3 set-index bits 12-20 of the PFN) is almost the same in every process: 38,828 pages, chi2/dof 0.37-0.53 (more even than random, as huge pages give), busiest colour 1.20-1.31x the mean. Correlation of ns with chi2/dof is r = 0.03 and with busiest/mean r = 0.39, the latter confounded by time (busiest/mean drifts up with run index, r = 0.68). So page-colour imbalance does not explain the spread. The time series has structure: runs 1-10 median 12.8 ns, runs 11-18 median 22.7 (up to 42.2), runs 19-24 median 14.5, lag-1 autocorrelation 0.47, i.e. the slow stretches come in episodes across consecutive processes rather than as independent per-process draws. That points to a machine-state cause (other-core or memory-controller activity, kernel background work, or memory fragmentation changing over time) and away from per-process page placement; the earlier reading of a per-process mode should be treated as a time-varying effect.

*Machine-state test (2026-10-22, no root, SMT sibling online, desktop session running, 30 processes with `/proc/vmstat` and `/proc/stat` deltas per process):* ns 11.8-26.0 (median 14.2). Memory management is ruled out: compaction stalls, compaction scans, page migrations, THP fault fallbacks and khugepaged collapses were all 0 in every process, THP allocations were 30-40 and the process's huge-page memory was a constant 60-62 MB (r = 0.01 with ns). What does track the time is the busy time of the *other* cores during the run: r = 0.82 between ns and the percentage busy of all cpus except core 2 (0.96-4.7% of 15 cpus, so well under one core on average); `pgfault` r = 0.62 (system-wide, probably the same activity). Controlled follow-up, 10 interleaved triples on core 4: no co-runner median 14.2 ns, an ALU spin loop 13.5, a random-read co-runner over a 16 MB array 13.2; neither reproduced a slowdown, so one L3-polluting thread or a busy sibling core is not enough to cause the episodes. Reading: the spread comes from activity of the desktop session on other cores (likely through shared memory bandwidth, the iGPU shares system DRAM, or L3 evictions by many small bursts), not from the harness, the allocator or page placement; the correlation is not a proof and the mechanism was not isolated. For publication numbers at 1M gates and above, run in a stripped session (no browser or compositor activity) or report the median and spread of many processes.

Core switching was checked and is not it: in 14 processes the harness was always on core 2 (`/proc/PID/stat` field 39 sampled every 50 ms; `taskset` pins it), and effective frequency was constant at 5.46-5.50 GHz. Preemptions of the harness on core 2 (`nonvoluntary_ctxt_switches`, 2-28 per process) do correlate with ns (r = 0.69, n = 14): something else is being scheduled onto core 2 during slow runs and evicts its caches, which fits the other-core-activity finding; the sizes are small (a few dozen switches per second) so the cache-refill cost per preemption would have to be large, and this was not isolated. The b17 `rx-prop` mode on the laptop was not examined here.
