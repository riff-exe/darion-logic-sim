# Darion Logic Sim: working notes for Claude

Gate-level logic simulator: Cython/C++ engine in `reactor/` (flat 24-byte `CPP_Gate` structs, branch-free SIMA evaluation), an object-oriented comparison engine in `reactor_oop/` (heap-allocated C++ subclasses with a virtual `compute()`), a pure-Python reference engine in `engine/`, a Python UI and API (the engine and API are the author's own work; the UI was built by a friend, so do not attribute UI work or UI claims to the project's research contribution). Darion is single-threaded and is not meant to compete with Verilator; it is an API with a UI whose point is being interactive and observable (load in milliseconds, toggle, read any gate, see changed gates) at usable speed. Live gate retyping is only used during IC creation: it is not a user feature, do not build on it.

Research state: `research/Claims.md` (numbers, per claim), `research/Paper_Notes.md` (explanations, evidence map, reviewer Q&A, reproduction commands, open items), `research/Timing_Report.md` (delay model, finished), `research/Related_Works.md`, `tests/benchmark_documentation.md` (older, partly superseded; check the claims doc first). Open work is in `TODO.md`.

## Before you build anything: check what already exists
Search this list, then the repo, before writing a script, running a benchmark or measuring something. Most questions already have a tool or stored data.

### Tools (use these, do not write new ones)
* **Full benchmark pipeline:** `tests/master_test.py <suite dir> [--vectors N --filter X --limit N --skip-load --skip-verify --skip-perf --no-engine --no-rx-oop ...]`. `run_all_test.sh` lists the exact invocations used for each suite.
* **Per-engine runners** (`tests/src/`): `benchmark.py` (combinational: ISCAS85, EPFL), `benchmark_iwls.py` (IWLS/ITC99/OpenCores/Faraday, sequential), `benchmark_89.py` (ISCAS89). `load.py` = memory + load time. `verifier.py`, `verifier_iwls.py`, `verifier_89.py` = output verification against Icarus and Verilator. `iwls_sequential_harness.py`, `iscas89_sequential_harness.py` = reference testbench generators.
* **PMU counters:** `tests/src/perf.py <suite or file> [--filter --limit --vectors N --no-engine --no-rx-sweep --no-icarus --no-verilator]` runs rx-prop and rx-oop pinned to core 2 and prints a table. It does NOT average: one call is one run. For repeats, loop over calls (the PMU table rows to grep are lines containing `rx-prop` / `rx-oop`; the OOP row starts with `|  |`). `tests/src/pmu_harness.py` has the event discovery; `tests/pmu_harness.py` re-exports it.
* **State verification vs Icarus/Verilator** (every flop plus outputs, long runs): `tests/verify_state.py <circuit> [--stim bench|run]`; real CPU workload: `--workload tv80 --cycles N`; bug-localisation case study (tv80 with one injected 2-input cell swap, Darion API versus Icarus compile/VCD flow, timed): `--case-study --seed N` (results in Claim 7). The tv80 environment is the `Tv80Darion` stepper class in that file.
* **Correctness suites:** `tests/integrity_test.py` (the 2026-10-21 run reports 28,115 passed, 0 failed in its master summary, 28,024 of them in the core and stress section; the older figure of 2,735 is out of date), `tests/test_timing.py --suite topologies|extended|bench`, `tools/verify_conway.py`, `tools/verify_timed_conway.py`, `tools/verify_timed_random_circuits.py` (Conway's Game of Life and random-circuit checks; the `.dig` files and stored states in `tools/` come from the Digital simulator, read the scripts before relying on this). The Digital Conway circuit is built on a lookup table (`cellLUT.dig`), so it is a correctness cross-check only, never a performance comparison with Darion. No interactive-simulator (Digital, Logisim) benchmark exists and none is planned; do not propose one without a gate-level converter and the author's go-ahead.
* **Ablations** (`tests/ablation_eval.py`, one script, several modes): `<reactor_dir> <label> b14 b15 ...` = SIMA vs `switch(type)` in the real engine from a scratch build (`-DDARION_EVAL_SWITCH`); `--export <reactor_dir> <suite/>circuit out.net [raw]` = dump a settled gate array plus the benchmark vectors (suites: itc99, opencores, iscas85, epfl); `--ui-cost <dir> b15 prop|sweep` = visual-queue cost; `--latency <dir> b15` = API call latency. `tests/ablation_layout.cpp` = standalone C++ harness (variants a heap+virtual, b arena+virtual, c flat+switch, d flat+SIMA, e flat32, g flat40; synthetic topologies chain/tree/random/mixchain or `--netlist` from the exporter). Build and options are in its header.
* **Gate-for-gate export to Digital and Logisim-evolution** (`scripts/iscas_parser.py <file.v> --export dig|circ --out <dir>`): one native gate per Verilog gate, nets joined by tunnels, `buf` merged into a wire; verified on 16 ISCAS85/EPFL circuits against an independent Python evaluator (Digital: 100 vectors through `java -cp Digital.jar CLI test`; Logisim: 8 constant-input variants through `--tty table`, because `-w` crashes headless in 5.0.0). Pin offsets were probed, not documented; Logisim ignores floating gate inputs, so always verify. Java and both tools are not in the repo: they were downloaded to the session scratchpad (Temurin 21 JRE, Digital v0.31, logisim-evolution 5.0.0). `flatten_darion_json` in the same file exports the exact gate netlist Darion simulates (sequential circuits included, flops expanded into gates) to the same Digital writer. Digital timing comparisons were run (Paper_Notes 3b-3d, scratch scripts in the session scratchpad, not in the repo): ISCAS85/EPFL, s5378 and b15 agree; tv80 does not run correctly in Digital because Digital's own oscillation limiter fires at step 0 and closes the model silently (confirmed with an error observer).
* **Other:** `tests/cache_test.py` (fragmented vs sorted memory), `tests/geometry.py` (topology statistics), `tests/ic_circuit_benchmark.py` (IC create/save/load), `tests/CLI.py`, `scripts/{iscas,iwls,epfl}_parser.py` (netlist to JSON), `scripts/merge_markdowns.py`, `tests/timing_lib.py` (helpers/oracles for the timing suites, also imported by the retype test).

## Build and run
* Build the engine: `bash scripts/build.sh` (add `--reactor-oop` for the OOP engine). `.so` files are written into `reactor/` and are git-ignored.
* Python: `.venv/bin/python`. Scripts that import the engine need `reactor/` and `editor/tools` on the path: run with `PYTHONPATH=editor/tools` from the repo root (many scripts add `reactor/` themselves; without `editor/tools` you get `No module named 'timing_tracer'`).
* References: Icarus Verilog (`iverilog`, `vvp`) and Verilator are installed. Machine used for every number: AMD Ryzen 7 9700X (Zen 5), 32 MB L3, `perf` user-mode counters work (`perf_event_paranoid=2`), pin with `taskset -c 2`.
* `.gitignore` ignores `*.json` and `*.txt` except demos and `tests/src/DFF*.json`, so new data files must use another extension (e.g. `.net`) or live in scratch.

## Rules
* Do not commit or push unless asked. The user commits `reactor/` themselves.
* Do not edit `reactor/` for experiments. Build a scratch copy and point the harness at it (see `tests/ablation_eval.py`).
* Benchmarks and `perf` runs need the CPU to themselves: do not run builds, tests or other benchmarks at the same time. Pin to one core (`taskset`), interleave variants across repeats, report median and spread.
* Read a whole results table before quoting it. Several earlier mistakes came from reading the first rows only (for example the cache sweep covers 100 to about 985k gates, not 913). Check the grep/parse pattern returns every row you expect (the OOP row of the PMU table was silently dropped once).
* Report results as measured. If a result contradicts a claim, write that into the claims doc; do not soften it.
* Do not add scripts. Extend an existing one (see the list above) or add a mode to it; the user does not want `tests/` cluttered. If a new tool is truly needed, say why nothing above covers it.
* Scratch files go in the session scratchpad, not in the repo.
* Do not assume what a feature is for. If unsure whether something is user-facing (retype, edit operations, UI behaviour), ask or read the code first.

## Framing
* The parsers and exporters in `scripts/` (`iscas_parser.py`, `iwls_parser.py`, `epfl_parser.py`, the Digital/Logisim export, `flatten_darion_json`) and the `.v` loaders in `tests/src/` are test and benchmark tooling, not Darion features. Darion's own input is its JSON circuit format. Never describe netlist import/export as a product capability or a contribution.
* Tone for any paper text: bridge the gap, do not compete. Describe Verilator, Icarus and Digital as complementary points on a spectrum, report comparisons as positioning not wins, no "beats"/"outperforms" wording, and state where the others are ahead.
* Darion is judged as correct, well-tested engineering with a measured design argument (data-oriented layout and branch-free evaluation versus an OOP object graph), not as a "faster than Verilator" result. The positioning is an interactive, observable simulator with usable speed; Verilator and Icarus are references and correctness oracles. The paper is positioned against Icarus and Verilator (industrial simulators, as baselines/oracles) and Darion's own OOP engine; the Digital comparisons are reserve material, not the main narrative (author's decision). Never write "faster than Verilator" without the qualifiers in the claims doc (Verilator wins 17 of 21 ITC99 circuits).
* Timing and delay system is finished; do not reopen it.
* Native flop evaluation ("flop-cut") was an experiment and has been removed from the repo. Macros are the planned future direction.
* The harness (`ablation_layout.cpp`) attributes the OOP gap; the headline measurement is the full-engine master-test data. The harness ratio runs about 0.25 below the engine ratio and that is accepted.
